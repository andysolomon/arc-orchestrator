    [x] 13.8 - Map workload_class to capabilityFloor, dual-accepted during migration; demote workload_class to observability metadata. capability-floor.ts (capability-floor/v1) supplies the mapping ADR 0011 left open, but NOT as the table both ADRs assume - four facts about the class vocabulary, none visible from the names. (1) The floors are DERIVED, not authored: a class's floor is the band its authored lead already occupies, resolved through the same candidateStackForRoute the live router uses, so "do not go below what this class leads with today" is the migration guarantee stated exactly rather than a judgment about a name; an authored column would be 13.9a's failure again, a hand-maintained scalar beside the data it summarizes. Read off the LOWEST ranked rung of the lead, because a stableId spans several and today's dispatcher may run any of them - the highest would set a floor stricter than the thing being migrated, and a migration that starts refusing work it used to do is not one. (2) The ladder is NOT monotone and was never meant to be: medium-light-work/medium-work and hard-light-work/hard-work hold identical candidate sets with the first two swapped, so -light- marks usage headroom rather than difficulty, and where the two leads sit in different bands the LIGHTER class gets the higher floor - the cost trade test/workload-ladder.test.ts already excuses. medium-hard-work and hard-work both lead with fable-5, so no snapshot can ever separate them. Seven names, five leads, one sanctioned inversion; an authored column would have had to fabricate the missing distinctions or drop the real one. (3) Degradation latitude is already authored, as automaticFallback: a fallback stack runs its tail down to the weakest member (composer-2.5 on every automatic implement stack), so minimumFloor 0 is the faithful translation, and a pinned stack has nowhere to fall (minimumFloor === capabilityFloor). Migration grants no latitude the stacks did not already have; widening it stays ADR 0011's TaskBudgetPolicy decision, which this takes half off the table for. (4) Two classes state a CEILING, not a floor: default pins composer-2.5 and light-work pins grok-4.5, cheap and fallback-free, and carrying only a floor inverts them - floor 0 admits everything and select() orders by band descending, so the cost-pinned classes would lead with the MOST capable rung available. bandCeiling (the eco-mode vocabulary ADR 0010 already has) is therefore a correctness requirement, with a test that shows the uncapped selection picking the dearest rung. Two consequences stated rather than discovered: deriving the floor is what keeps the rollback real, since select() rejects an unranked rung against any floor above 0 and a guessed non-zero floor would turn ADR 0010's "delete the snapshot" into a refusal of every medium-and-up dispatch - with no snapshot every derived floor is 0 and the cost pins lose their ceiling too, which is what rollback costs; and a derived floor can NEVER be unreachable because it is always a band some rung occupies, where a hand-authored table could assign hard-work a floor of 4 that needs a score above 0.8 no published suite approaches, refusing every dispatch while looking like a considered policy. Dual acceptance: the explicit floor wins (it comes from the state that is dispatching) and the derived floor is returned beside it either way, because the migration question is not which floor ran but whether the two agree and 13.10's corpus cannot measure that if the loser is dropped at the seam; an explicit floor does not inherit the class's ceiling. The demotion is ENFORCED, not asserted: capability-selection.ts contains no reference to workload_class and a test fails if one appears. bandForSnapshotEntry was exported from capability-selection.ts rather than restating decision 0005's precedence rule, which is the drift 13.9a found.
